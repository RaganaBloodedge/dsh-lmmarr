# 会话内上下文节流与冷存重建（context-throttle）

> 分工：`lmmarr-memory` 管**跨会话的任务结构**（谁依赖谁、做到哪了）；本文这套管**会话内的节流与重建**（每轮往模型里塞什么）。
> 两套共用同一份冷存储，不抢目录。

---

## 0. 一句话

**主上下文只装「结论 + 指针」**。过程、原文、失败重试——要么**不进**（子代理），要么**压掉**（执行器），要么**可回收**（冷存储 journal）。

---

## 1. 三条杠杆（按收益排序，来自 RPGBar 实测）

| 杠杆 | 实测依据 | 手段 |
|---|---|---|
| **① 转数** | 调用数 ×0.6，收益是第二名的两倍 | 组合型操作固化成脚本（一行调用 = 一轮） |
| **② 每轮上下文体积** | `Read` 带 limit → ×0.86 | 读前先 grep、必带 limit、输出去字节留结论 |
| **③ 重复读** | 53% 的文件被读过不止一次，`main.py` 62 次 | 同文件不重复读、大探索走子代理 |

**反直觉红线（勿踩）**：**绝不能"把历史压缩重写"**。实测 cache 命中 99.1%（等效 0.1x 价），任何改写**已缓存前缀**的动作会把 0.1x 变成 1x，**成本反而上升**。
→ 正解：**只对"今后新产生的内容"节流，不动已缓存的前缀。**

---

## 2. 三个原语与它们的容器（回答"子代理能否做成 skill"）

**结论：不能。** skill 的清单只有 `name` + `description`，它没有声明子代理或钩子的字段。子代理和钩子是**插件**的清单项。

| 原语 | 是什么 | 声明在哪 | 强制力 |
|---|---|---|---|
| **Skill** | 静态说明 + 脚本，加载进**当前**上下文 | `~/.workbuddy/skills/<n>/SKILL.md`，或插件的 `skills/` | **仅建议**（模型可以选择不听） |
| **Agent（子代理）** | 独立 agent 实例，**自己的上下文窗口**，只有最终消息回父级 | 插件的 `agents/*.md`（`plugin.json` 的 `agents` 字段）；另有内置 Explore/Plan/general-purpose | **隔离**（过程物理上回不来） |
| **Hook** | 生命周期事件触发，配置在上下文之外，**确定性** | 插件的 `hooks/hooks.json`（`plugin.json` 的 `hooks` 字段） | **强制**（不经过模型判断） |

**硬证据**：本机 `workbuddy-docx` 插件的 `.codebuddy-plugin/plugin.json` 同时声明三者：

```json
{
  "hooks": "./hooks/hooks.json",
  "skills": ["./skills/brief-compose", "..."],
  "agents": ["./agents/doc-converter.md", "./agents/doc-formatter.md", "./agents/doc-writer.md"]
}
```

### 由此得到的三条推论

1. **skill 能"指挥"子代理**：SKILL.md 里写清"何时委派、brief 怎么写、返回什么契约"，主 agent 读后就去调内置的 Agent 工具。这是"子代理用法做成 skill"唯一真实的形态——**它是说明书，不是执行体**。
2. **skill 不能"成为"子代理**：skill 和它的 scripts 都**没有 LLM**——脚本是普通 OS 进程。没有 LLM 就没有 agent。
3. **要"彻底解决"必须上插件层**：强制（hook）+ 声明自定义子代理（agents）都在插件清单里。**"彻底"= 隔离（子代理）+ 强制（hook），不是"multi-agent"。**

## 3. 四层能力

```
L4 委派   大探索走子代理      → 过程永不进主上下文（50k in / 1.5k out）
L3 沉淀   journal + brief     → 让"删"变安全（lmmarr 已有，扩展 journal 语义）
L2 纪律   grep/limit/并行     → 每轮体积 ×0.86、消除重复读
L1 执行器 固化成脚本，一行调用  → 转数 ×0.6（第一杠杆，收益最大）
```

### L1 执行器（收益最大，也是最初漏掉的一层）

把高频操作固化成脚本，**一行调用，只回结论**。

- **预置**执行器（skill 自带 `scripts/`）：源码 **0 次**进历史，立刻划算。
- **现场写**脚本（agent 临时写）：源码进一次历史后被重发 ~63.8 次，复用 **≥2–3 次**才摊得平。

判据：**同一模式写到第二次就固化。**

### L2 节流纪律

读前先 grep、`Read` 必带 limit、同文件不重复读、独立调用**并行发**、大块探索走子代理。这条是纯纪律，靠 L4 与 hook 兜底才有强制力。

### L3 冷存储 journal（lmmarr 已有，扩展写入语义）

每任务一份 append-only，条目只有四类：

```
- did   #12  改 main.py 加重复惩罚 → 5 条断言通过        （不记 diff 原文）
- pit   #7   中文 PDF 文本层按列倒序 → 提取失败；识别特征=单字碎片；处理=直接放弃
- open  #9   smoke_test 第 3 例 flaky（复现：连跑 5 次 1 次失败）
- next       补第 4 例
```

**报错生命周期**：`open`（未解决，留最小复现）→ 修好后**降级为 `pit`，删掉报错原文**，只留"特征 + 处理法"。
思考过程、工具原文、路径清单一律不进。

`brief` 命令：按任务 + 关键词从冷存储拼一段 ≤1200 字符指引（目标 / 已定决策 / 相关坑 / 未解决 / 下一步 / 文件指针），**零 LLM 调用**。

### L4 委派（隔离层）

**唯一机制**：子代理读 50k token 的文件/日志/搜索结果，**只回 1.5k 摘要**；此后主对话每一轮背的是 1.5k，不是 50k。

## 4. 执行器输出协议（结构强制，不靠自觉）

```
成功（exit 0）：
OK    <一行结论>
KEY   <关键字段>: <值>          × 最多 5 行
DETAIL <路径>                   ← 中间过程写文件，要看时再去读

失败（exit ≠ 0）：
全部 stderr + 最小复现片段      ← 你说得对：失败时返回整段，调试不会变难
```

stdout 恒定压在 ~10 行内，并给"细节去哪找"的指针。**成功态卸载是结构强制的。**

---

## 5. 委派纪律（brief 契约 + 返回契约）

**委派出去的 brief 必须自包含**（子代理看不到主流程历史）：

```
【目标】<一句话>
【已知】<关键事实，≤5 条>
【产出】<只要结论，格式：...>
【禁区】不要回贴原文；不要回贴中间过程
```

**返回契约**：子代理默认只回最终消息。要在自己的 prompt 里钉死"只回结论 + 指针"，否则它会把原文再吐回来。

---

## 6. 触发条件（长程任务才启用）

- **短程任务不启用**：一次性/几步就完的，写脚本的成本摊不平，包住只会更慢。
- **足够长才触发**：出现"同一模式第二次出现""上下文开始逼近上限""任务已跨多轮"等信号时启用。
- 与 Claude Code 的 skill 加载模型一致：**启动时只挂 name + description，正文在被调用时才加载**——不启用时零成本。

---

## 7. 成本与边界（诚实）

| 事实 | 数字 | 含义 |
|---|---|---|
| 子代理**总** token 变多 | 多代理 ≈ 15× chat；单代理 ≈ 4× chat | 它**不是省总 token**，是**省主上下文** |
| 子代理启动成本 | 自带 system prompt + 工具定义，**每轮**都发；**首个请求不吃父级 cache** | 短任务用它是纯亏 |
| 多代理在编码任务上不划算 | Anthropic 原话：多数编码任务可并行度低于研究，且 agent 之间实时协调还不成熟 | **不要做 swarm** |
| 独立测评 | Google/MIT：多代理每千 token 完成任务数 **低于**单代理（每种架构都如此） | 别为了"多代理"而多代理 |

**所以本设计不追求 fan-out 多代理**，只保留**单主 + 偶发 worker 委派**：主 agent 掌全局，只在"大探索"时丢一个 worker 出去，拿回一段结论。这是"隔离"，不是"协作"。

---

## 8. 探索性工作：两条相反的需求

探索不是"一种工作"，是**两段**，需求正好相反：

| 阶段 | 需要什么 | 为什么 |
|---|---|---|
| 探索**中**（live） | 观测必须**在** | ReAct 每一步依赖上一步的观测，删了就走不下去 |
| 探索**后**（done） | 轨迹必须**走** | 留着每轮重发；**40.4% 的读取在 2 次调用后文件已变**——"留着不只是没用，是**错的**" |

**问题的真身**：探索从不"宣布结束"，所以轨迹永远停在 live 状态，一直被复用。
→ 要的是**退休机制**，不是"少探索"。

### 三条退休路径

| 路径 | 机制 | 适用哪种探索 | 谁执行 |
|---|---|---|---|
| **进不来** | 执行器（预固化脚本，输出 ~10 行） | 可预先指定的（"找所有调用者并统计"） | skill `scripts/` |
| **出不去** | 子代理（隔离，只回结论） | 自包含的——**宽并行**或**深串行**都算 | 内置 Agent 工具 |
| **就地退休** | 掩码（滚动窗口 → 占位符/指针） | 必须留主线的**逐步依赖型** | **框架 / hook** |

### 一个必须纠正的框定

**子代理不是只给"宽并行探索"用的。** 单个子代理跑串行深挖、只回结论，同样成立——你没拿到并行，但拿到了**隔离**。
代价是每个子代理的固定开销（自带 system prompt + **首请求不吃父级 cache**），**但单子代理远比 fan-out 便宜**（fan-out 才是 15×）。
→ 所以"探索"里**大部分都能委派**，只有"主流程必须**逐步消费每个中间结果**"的那种不能。

### 真正不能委派的残留：主流程逐步依赖型

对这种，只有**掩码**能救，而掩码是**框架层能力**——模型改不了自己已进窗口的旧观测。skill 只能做两件半：

1. **带问题去探索**：探索前写下一句"这次要回答什么"。问题答完 = 退休点。
2. **答完即登记**：答案落 journal（did/pit/open/next）+ 指针，**停止引用原文**。
3. （半件）**压缩入口体积**：grep 定位再读、带 limit、不重复读。

### 为什么"垃圾被复用"不只是花钱

JetBrains 实测：掩码让 solve rate **+2.6%**；而 LLM 摘要**降低**它（摘要抹平了"该收工"的信号）。
→ 退休不只是省钱，是**提高正确率**——因为陈旧观测会**误导**（模型要花力气从 50k 陈迹里翻出 1k 有效信息）。

### 掩码与 cache 的冲突怎么解

掩码会改写已缓存的前缀（0.1x → 1x）——所以**必须批处理**：攒到阈值一次性退休一大批，付一次重读，随后重新缓存。Anthropic 的 `clear_at_least` 就是干这个的。**绝不能每轮掩一点。**

### 能力门（已实装）

`skill/tools/agents-probe.mjs`（零依赖）回答"当前框架有没有子代理"，输出 **`MODE delegate|self-compress`**：

- `delegate` —— WorkBuddy / Claude Code **恒为 yes**（内置子代理一直在）→ 委派，只回结论。
- `self-compress` —— 裸 API 循环等无子代理环境 → 只留结果与关键节点。

探测顺带列出已安装的**自定义**子代理（有则优先用——它们能被打死"只回结论"）。
**边界**：`no` 分支是为**可移植性**准备的；在本机实测恒为 `yes`。它只回答"允许不允许委派"，不判断该委派哪部分。

## 9. 与 lmmarr 的关系

| 能力 | 归属 | 形态 |
|---|---|---|
| 跨会话任务结构（索引 + 关系图 + 进度） | `lmmarr-memory` | skill（已装） |
| 冷存储 journal + brief | 扩 `lmmarr-memory` | skill（待做） |
| 执行器库 + 输出协议 | 新 | skill `scripts/`（预置） |
| 委派纪律 | 新 | skill 正文（advisory） |
| 强制 + 自定义子代理 + hook | 待定 | **WorkBuddy 插件**（若要"彻底"） |

**下一步的岔路**：只做 skill（建议层，够用且轻）vs 打成插件（上 agents + hooks，才有强制力）。
